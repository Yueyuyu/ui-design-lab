# 设计理念套系规划

更新：2026-09-18。定位已按用户反馈确认；首批 Apple 与 ChatGPT 方向已实现为 experimental；其他方向仍处于研究规划阶段。

## 产品定位

UI Design Lab 提供可被其他项目与 Agent 消费的独立设计语言。成熟软件或平台可以成为一套语言的主要来源：提炼其信息组织、字体、密度、组件结构、导航和交互规则，再用原创实现支持不同业务。

组织关系为：设计来源 → 独立套系 → foundations / components / patterns → 可操作场景 → 项目接入。设计来源不是代码依赖，也不代表官方合作或官方组件库。

套系身份由一组可复用的设计决策决定。设置页、资料库、任务台和对话页是场景；同一场景可以由多个套系实现，同一套系也应能支撑多个场景。无需让每个套系覆盖全部业务；适用范围与未支持能力必须明确。

用户进一步澄清：沿现有五套的组织方式继续增加完整组件套系，可以扩展到很多套。同类按钮、输入、菜单、导航、弹窗等允许在各套中独立实现，供消费项目按喜好与需求选择。新增套系不要求独有业务场景，也不要求先完成两个不同场景；先保证本套组件语言完整、一致、可运行、可导入。

## 方向与后续候选

以下是项目的提炼方向，不是第三方官方原则的逐字转述，也不代表已完成对各产品当前版本的视觉研究。除上方两套已实现方向外，其余候选暂不分配 suite ID 或计入可用数量。

| 主要来源 | 拟提炼的语言 | 首批验证场景 | 扩展边界 |
| --- | --- | --- | --- |
| Apple HIG 与具体系统应用 | 内容优先的层级、分组列表、主从导航、直接反馈、空间一致的浮层与动效 | 偏好设置、个人资料库 | 先选定桌面来源；移动布局在同套内另行验收 |
| ChatGPT | 对话与正文主导、克制工具区、渐进展开、连续任务反馈 | 对话助手、带结果侧栏的研究/写作 | 消息服务、流式结果、停止与重试由消费项目适配 |
| Linear | 精确对齐、稀疏列表、键盘优先、快捷创建、非模态详情 | 议题处理、项目计划 | Harbor Desk 为可考虑的独立名称；保留与表格后台的结构差异 |
| 小米具体应用，优先米家 | 状态可读、分组卡片、直接控制、明确的操作结果 | 设备管理、日常场景配置 | 固定一个主要应用来源；HyperOS 的设置或系统控件需单独核对版本 |
| Google Material Design | 语义化颜色与层级、自适应导航、清晰状态反馈 | 移动任务、跨屏资料管理 | 后续候选；有消费需求再启动 |
| Microsoft Fluent | 桌面生产力、工具命令、分栏与信息密度 | 文件管理、业务工作台 | 后续候选；先评估与现有套系的实际差异 |

首批 Apple 与 ChatGPT 套系已完成基础交付；Linear、小米及其余方向按实际接入需求排序。既有五套继续维护，不同时为所有候选生成空壳。

## Apple 方向的首轮边界

本节保留设计方向；当前已实现范围以 Orchard UI 的 suite.json、DESIGN.md 和 API.md 为准。资料库、底部面板等未列出的能力仍是后续候选。

- 理念与来源：以 [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/) 为官方规范入口，选定同一平台的设置与资料浏览界面作为视觉依据。研究记录区分官方规范、页面观察和本项目适配决策。
- 字体：使用系统字体并保证 Windows 与中文回退。以字号、字重、行高和留白共同建立层级，支持文本放大；不随包分发未授权字体。
- 布局：桌面采用侧栏、主内容与按需详情；移动另行定义单列进入/返回及合适的导航，二者保持数据与语义一致，不强求相同的页面几何形状。
- 密度：正文可读优先，列表与工具区按任务收紧；舒适/紧凑是套内模式，分别验证，不靠缩小所有字体制造紧凑模式。
- 组件结构：优先形成分组设置行、选择与开关、分段控件、搜索、导航列表、工具栏、主从容器、菜单、弹窗/底部面板等可组合能力。完整设置页和资料库归入 patterns，不计入基础组件数。
- 交互：按下即反馈，执行结果准确回显；浮层有明确来源与退出路径，支持键盘、焦点恢复与取消。连续操作可中断，手势提供可见控件替代。
- 动效与材质：动效解释状态与位置关系；半透明只服务必要的层级，正文保持稳定可读，并提供减少动态、减少透明度与高对比的适配。用户此前对装饰性玻璃拟态的排除仍有效。
- 可选演示场景：设置页可验证修改、保存、取消与失败恢复；资料库可验证搜索、选择、详情、空结果恢复与键盘导航。按组件交付进度补充，不作为新增套系的数量门槛。
- 服务边界：示例使用原创数据，真实认证、文件存储和业务 API 由接入项目提供；本地演示结果与真实业务采用分开记录。

## 每套的交付结构

| 层级 | 应交付内容 | 消费者得到什么 |
| --- | --- | --- |
| 设计理念 | DESIGN.md、来源记录、适用任务、局限 | 理解何时选用、何时不适合 |
| 基础规范 | 字体、颜色、间距、圆角、密度、动效与可访问性规则 | 扩展页面时仍保持同一语言 |
| 组件 | 独立实现、类型、API、七态与真实预览 | 按需导入到现有业务 |
| 页面组合 | 按组件能力逐步补充设置、内容、任务等场景 | 得到可修改的完整流程 |
| 分发 | 版本化组件包、样式入口、Starter、兼容声明 | 无需复制整个实验室即可使用 |
| Agent 消费 | suite.json → DESIGN.md → API → 对应环境的消费校验 | 自动采用正确组件、作用域和规范 |

沿用当前仓库对套系隔离、声明生成和包外消费的要求。实验室内运行 `suite:check`；业务项目按消费技能运行检查，不要求它携带实验室源码。新套系的 React 18/19 兼容需实际验证，不能直接继承现有五套的测试结论。

## 网站与命名

公共首页继续使用唯一套系目录。套系主标题使用自主名称，来源理念放在详情中可读、可追溯地说明；场景页保留“我要做什么”的选型路径。这两种入口最终指向同一个套系，不产生重复套系。

主要来源与参考平台应清晰，避免把多个品牌的不同规则无选择地混在一套。可借鉴通用设计理念，公开资产的使用与分发继续遵循 NOTICE.md；不把第三方商标、字体或截图自动纳入组件包。

## 完成标准

1. 选定并记录具体视觉来源，明确平台、页面、版本或访问日期；区分事实、观察与自主适配。
2. 创建独立 draft 套系，提供可操作展示及基础规范；不以空 manifest 宣称可用。
3. 同类组件在本套中遵循一致的布局、字阶、密度、结构与交互规则，体现选定来源的设计语言；通过真实预览和组件组合验证，不以业务场景的独有性或数量作为门槛。
4. 完成七态、键盘/焦点、窄屏、减少动态、样式隔离、类型、构建与包外消费验收后，按交付合同进入 experimental。
5. 实际采用、维护承诺与发布状态分别记录；没有证据时不宣称真实采用或官方认可。
