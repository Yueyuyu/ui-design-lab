# 用套系设计自己的产品

用户只需提供所选 Suite ID 和产品需求。获取源码、读取规范、按需安装、扩展设计与验证由 Agent 完成，不要求用户粘贴整份规范或接口声明。

## 先获取同一版本的资料

- 官方仓库：https://github.com/Yueyuyu/ui-design-lab ，默认分支为 `main`。本指南的仓库位置是 `skills/consume-suite/SKILL.md`，套系位置是 `systems/<id>/`。
- 先检查当前业务项目的约定、技术栈和依赖。保留业务代码、未提交修改、路由、认证与锁文件约定。已安装此包时，优先读取已安装版本的指南和套系规范，不静默升级或把在线最新接口混入旧版本。
- 未安装时，将 `https://github.com/Yueyuyu/ui-design-lab.git` 的 `main` 分支克隆到独立临时目录，不覆盖当前项目。在克隆目录执行 `git rev-parse HEAD`，记录本次使用的提交 SHA；之后所有规范和源码都从这一提交读取。使用 GitHub API 获取文件时也先解析分支 SHA，再按该 SHA 读取。
- 核对根 `package.json` 和 `systems/<id>/suite.json`。套系必须实际存在，`draft` 尚不支持正式接入；版本号相同不保证不同提交的内容完全一致。找不到套系、文件或无法访问 GitHub 时，指出缺失项，不猜测 API、不擅自换套系。
- 只读取所选套系及当前任务相关资料，不把整个仓库一次性塞入上下文。需要时继续读取相关规范和相近源码。

## 按技术栈接入

- **React 项目**：先读该提交的 `package.json`，核实 `exports`、`peerDependencies` 与构建脚本。在独立源码目录执行 `npm ci`、`npm pack`；`prepack` 会构建组件库。把实际生成的 `.tgz` 放入业务项目合适的本地依赖目录，再用项目原有包管理器安装。记录来源仓库、提交 SHA、包版本和 Suite ID，保留锁文件中的完整性信息。不要猜测 npm 已发布或 GitHub Release 存在包附件。
- **其他技术栈**：无需安装 React 包；按下方顺序读取设计语言，在现有技术栈中实现。规范、Token 与交互原则仍然适用，不自动迁移框架。
- 安装失败或缺少必要资料时，保留现有项目并说明具体原因。已有示例只用于参考，不能用运行示例替代用户的实际产品需求。

## 读取设计语言并实施

1. 确认目标 Suite ID 和实际使用的源码提交或已安装包版本。仓库内读取 systems/<id>；采用 React 包时读取 node_modules/ui-design-lab/systems/<id>。不能用在线最新文档推断已安装版本。
2. 按顺序读取 suite.json → DESIGN.md → standards/extension.md → foundations/tokens.json 与 token-bindings.json → 相关 standards → API.md → web/index.d.ts；有 INTEGRATION.md 时一并阅读。先理解设计逻辑，再了解现有 API。旧版本没有 extension.md 时，使用其已存在规范并明确缺失规则，不套用最新版本。
3. 将套系视为可以推导新设计的基础。明确用户、任务、内容优先级和主操作，再选择导航、页面层级、信息密度与窄屏顺序。已有场景只是应用示例；不机械继承其侧栏、业务字段或组件数量。
4. 简短列出此次设计依据：使用哪些语义颜色与字阶、为何采用该布局、哪些组件直接复用、哪些组合、哪些需要新增。规则明确时直接实施，不为例行设计决策反复要求用户批准。
5. 采用 React 包时，从 ui-design-lab/<id> 导入实际存在的组件及本套 tokens.css、components.css，使用 manifest.scope。相近组合优先复用；缺失的组件可以在目标项目内实现，沿用本套的表面、字阶、间距、形状、图标和交互语法。其他技术栈按上述设计规则新增组件。禁止编造包导出或混入另一套的视觉 Token、组件、素材。
6. 新组件放在项目自身组件目录，使用项目组件名与 class，在本套根作用域内引用真实 CSS 变量。先查看本套相近组件的类型和结构，再定义数据、回调、默认/悬停/按下/聚焦/禁用/加载/错误状态，以及键盘、响应式和低动态行为。不适用的状态说明由哪个子控件承载。
7. 新页面可以重新组织阅读、表单、数据、内容或工具区，不必采用已导出的整页工作台。品牌定制在项目主题层管理语义映射，保持文本对比、状态语义与套系气质；缺少 Token 时新增明确命名的项目 Token 并记录依据，不散落随意数值、不改写安装包。
8. 现有能力边界描述组件包已交付什么，不禁止用户实现新的业务 UI。新增日历、文件库、预约等须标作项目本地扩展，不能声称包原本具有该能力；新服务、平台适配或第三方素材权利也不会因复用视觉语言自动具备。
9. 在项目持有数据与服务适配器，处理真实读取、空数据、保存失败和取消。示例成功、浏览器保存不等于服务端成功。不要覆盖项目已有路由、认证或数据层。
10. 安装 React 包的消费项目可运行 `node node_modules/ui-design-lab/scripts/check-consumer.mjs --suite=<id> --source=src` 检查包内设计规范和静态套系导入；所有技术栈都运行项目自身构建及与改动相关的类型、交互验证。动态导入/作用域须人工复核；静态检查不证明视觉一致性或业务服务可用。
11. 只有修改实验室源码时才运行 npm run suite:check；消费项目不要求存在该脚本。交付时区分原有组件、项目新增组件、真实业务服务，说明规则如何应用、验证环境与实际覆盖流程。
